# План: мониторинг состояния компьютеров ПВЗ

Статус: **план согласован (05.10.2026)**, решения — раздел 8; работа в ветке `feature/health-monitor` до полной отладки.

## 1. Зачем

Компьютеры ПВЗ ломаются молча, и о проблеме узнают, когда что-то уже не работает:

- **144**: системный диск с июля сообщал Windows о скором отказе (SMART: резерв переназначенных секторов исчерпан —
  4095, 128 тыс. ошибок CRC по SATA), неустранимые аппаратные ошибки WHEA с декабря 2025, а 04.10.2026 — зависания
  и артефакты на экране. Scheduler на этом компьютере не работал с 21.12.2025 (старый код, нет пакетов и `.env`), и
  этого никто не видел: в Планировщике Windows у задач всегда стоял результат 0x1 (исправлено 04.10.2026).
- **143**: на системном диске `C:` осталось 11% свободного места; роутер перестал сохранять настройки.

Цель — каждый день собирать с каждого ПВЗ ключевые показатели в Google-таблицу, видеть их динамику и получать
уведомление в ВК, когда что-то ухудшилось, а также узнавать, что ПВЗ **перестал присылать** данные.

## 2. Общая схема

```text
Компьютер ПВЗ (раз в день)                         Google-таблица                     Снаружи
  HealthMonitorScript (tasks/system)
    1. сбор: диски/SMART, место, журналы Windows,
       состояние scheduler                ──────►  лист PVZ_HEALTH (строка ПВЗ/день)
                                                    лист PVZ_DISK_HEALTH (диск/день)
    2. сравнение с прошлым сбором (локальный файл
       состояния) → тревоги               ──────►  ВК (через utils/notifications)
                                                                                     Apps Script (по расписанию):
                                                                                     кто не прислал данные >26 ч → ВК
                                                    Looker Studio  ◄──────────────── графики и сводка по ПВЗ
```

- Сбор и тревоги «изнутри» — новая задача `HealthMonitorScript` в домене `tasks/system` (рядом с `UpdaterScript`):
  конфиг `config/scripts/health_monitor_config.py`, расписание собирается `collect_task_schedule` как у остальных.
- Хранение — те же механизмы, что у KPI: `GoogleSheetsUploader`, пакетный upsert (`kpi_upload_mode = batch`),
  та же книга (`SPREADSHEET_ID_PROD`) и сервисный аккаунт.
- Уведомления — `scheduler_runner.utils.notifications` (ВК), те же параметры подключения, что у reports.
- Проверка «кто молчит» — **вне** компьютеров ПВЗ (Apps Script в той же книге), иначе мертвый компьютер о себе не
  сообщит.

## 3. Что собирать

Сбор — один PowerShell-скрипт в составе задачи (`health_probe.ps1`), возвращающий JSON; Python разбирает, сравнивает,
пишет и уведомляет. Так данные Windows (CIM, SMART, журналы) берутся родными средствами, а логика и запись — в общем
коде проекта.

### 3.1 Лист `PVZ_HEALTH` — одна строка на ПВЗ в день

Ключ: `work_date`, `pvz_id`.

| Группа | Поля |
|---|---|
| Идентификация | `work_date`, `pvz_id`, `collected_at`, `computer_name`, `code_version` (коммит), `code_behind_main` (число коммитов позади `origin/main`) |
| Система | `os_version`, `boot_time`, `uptime_hours`, `cpu`, `ram_gb` |
| Место | `c_free_gb`, `c_free_pct`, `d_free_gb`, `d_free_pct` |
| Стабильность за 24 ч | `unexpected_shutdowns` (Kernel-Power 41 / 6008), `bugchecks` (1001), `whea_errors`, `disk_errors` (disk 7/11/51/52/153), `ntfs_errors`, `display_resets` (4101) |
| Диски (сводно) | `disks_total`, `disks_warning` (не Healthy / прогноз отказа), `worst_disk` |
| Scheduler | `task_operator_result`, `task_camera_result`, `task_system_result` (результат последнего запуска), `reports_last_success` (последний успешный `ReportsProcessor`), `copy_last_success`, `updater_last_success` |
| Итог | `status` (`ok` / `warning` / `critical`), `alerts` (коды сработавших правил через запятую) |

### 3.2 Лист `PVZ_DISK_HEALTH` — одна строка на диск в день

Ключ: `work_date`, `pvz_id`, `disk_serial`. Серийный номер, а не номер диска в системе: после замены или перестановки
диска история не перепутается.

`work_date`, `pvz_id`, `disk_serial`, `model`, `media_type` (HDD/SSD), `size_gb`, `volumes` (буквы), `health_status`,
`predict_failure`, `smart_5_reallocated`, `smart_197_pending`, `smart_198_offline_uncorrectable`,
`smart_187_reported_uncorrectable`, `smart_199_crc_errors`, `smart_9_power_on_hours`, `temperature_c`.

Атрибуты, которых у диска нет (у SSD часть отсутствует) — пусто.

### 3.3 Права

SMART (`root\wmi`, `Get-StorageReliabilityCounter`) и часть журналов доступны только с повышенными правами. Задача
`\Задачи system` запускается от администратора (`aniki`), но с уровнем `LeastPrivilege` — без повышения. Варианты
(решить на этапе 1, проверив, что именно недоступно):

1. **Уровень «наивысшие права» для `\Задачи system`** — одна настройка в задаче (и в эталонном образе); под ним же
   будет работать `UpdaterScript`.
2. Отдельная задача планировщика только для сбора (`HealthProbe`, «наивысшие права») — изоляция, но еще одна задача
   на каждом ПВЗ и в образе.

Скрипт в любом случае не падает без прав: недоступные поля пустые, в строке отметка `probe_limited`.

## 4. Тревоги (ВК)

Сравнение — с прошлым сбором из **локального файла состояния** (`C:\tools\scheduler\reports\health_state.json`): без
лишних чтений таблицы и работает при недоступном Google. Уведомление — только при **появлении или ухудшении**;
повтор неустраненной критической проблемы — раз в неделю.

| Код | Условие | Уровень |
|---|---|---|
| `DISK_PREDICT_FAILURE` | SMART: прогноз отказа / health не Healthy | critical |
| `DISK_REALLOCATED_GROWTH` | рост `smart_5` или `smart_197`/`198` с прошлого сбора | critical |
| `DISK_CRC_GROWTH` | рост `smart_199` (кабель/разъем SATA) | warning |
| `DISK_HOT` | температура > 50 °C | warning |
| `LOW_SPACE_C` | на `C:` свободно < 15% или < 10 ГБ | warning (< 5% — critical) |
| `UNEXPECTED_SHUTDOWN` | аварийные перезагрузки / BugCheck за 24 ч | warning (≥ 3 — critical) |
| `WHEA` | аппаратные ошибки WHEA за 24 ч | critical |
| `DISK_IO_ERRORS` | ошибки disk/NTFS за 24 ч | warning |
| `CODE_OUTDATED` | `code_behind_main` > 0 больше суток (обновление не проходит) | warning |
| `REPORTS_STALE` | `ReportsProcessor` не завершался успешно > 1 дня | warning |
| `TASK_FAILED` | результат задачи планировщика ≠ 0 (после исправления runner 04.10.2026 это реальная ошибка) | warning |

Текст — одно сообщение на ПВЗ: что случилось, значения «было → стало», что сделать (например «заменить диск,
перед этим — `prepare`/образ», «освободить место на C:»).

## 5. Проверка снаружи: кто молчит (Apps Script)

Отдельный скрипт в проекте Apps Script книги (рядом с failover), триггер по времени раз в день (например, 14:00):

- список ожидаемых ПВЗ — лист `PVZ_REGISTRY` (`pvz_id`, `active`, `expect_health`, `expect_kpi`) — закрытый ПВЗ
  (СОСНОВКА_10) просто помечается неактивным;
- ПВЗ без строки `PVZ_HEALTH` за > 26 ч → «ПВЗ молчит: компьютер выключен, scheduler не работает или нет интернета»;
- заодно: последняя строка `KPI` ПВЗ старше 2 дней → «отчеты ПВЗ не поступают» (дополняет failover);
- отправка в ВК через `UrlFetchApp` (токен — в свойствах скрипта, не в коде).

## 6. Дашборд

**Looker Studio** (бесплатно, источник — листы книги):

1. **Сводка** — последняя строка по каждому ПВЗ, цветом `status`, место на `C:`, худший диск, дата последнего отчета.
2. **Диски** — графики по `disk_serial`: переназначенные/ожидающие сектора, CRC, температура, наработка.
3. **Стабильность** — аварийные перезагрузки, WHEA, ошибки дисков по дням.
4. **Scheduler** — версия кода и отставание, результаты задач, последние успешные запуски.

Без Looker Studio — те же графики встроенными диаграммами на отдельном листе (беднее, но без внешнего сервиса).

## 7. Этапы

| # | Что | Проверка |
|---|---|---|
| 1 | `health_probe.ps1` + `HealthMonitorScript` (сбор → JSON → лог, **без записи**), решение по правам (3.3) | ручной запуск по SSH на 143 и 144: поля заполнены, на 144 видны проблемы диска |
| 2 | Листы `PVZ_HEALTH`, `PVZ_DISK_HEALTH` (конфиги таблиц), пакетная запись; расписание раз в день | строки 143/144 в таблице, повторный запуск обновляет, а не дублирует |
| 3 | Тревоги: файл состояния, правила раздела 4, ВК | искусственный порог (например, `LOW_SPACE_C` < 50%) → одно сообщение, повторный запуск — без повтора |
| 4 | Apps Script «кто молчит» + `PVZ_REGISTRY` | выключенный ПВЗ → сообщение на следующий день |
| 5 | Looker Studio | дашборд по данным 2–3 недель |
| 6 | Раскатка: все ПВЗ через `UpdaterScript`; права задачи — в эталонный образ (`docs/imaging`) | строки от всех активных ПВЗ |

Каждый этап — своя ветка, тесты, документация в том же коммите.

## 8. Решения (05.10.2026)

1. **Время сбора — 13:10** (runner задач `system` срабатывает в :10; при `time = 13:10` сбор идет в 13:10). Сбор —
   только чтение: запросы CIM/SMART, журналы событий с фильтром за 24 ч, размеры томов без обхода папок, `git` —
   несколько секунд, без заметной нагрузки. Окон у «Оператора» нет: `\Задачи system` выполняется от `aniki` без входа
   в систему (тип «с сохраненным паролем»), Python — `pythonw`, PowerShell сбора — без окна (`CREATE_NO_WINDOW`).
   Если на практике сбор окажется заметным — перенос на 21:10.
2. **Права — «наивысшие права» для `\Задачи system`** (вариант 1 из 3.3). Смена уровня у задачи с сохраненным
   паролем требует повторного ввода пароля `aniki` (Планировщик: свойства задачи → «Выполнить с наивысшими правами»);
   то же — в эталонный образ.
3. **Чат — тот же, что у отчетов** (ВК, `NOTIFICATION_CONNECTION_PARAMS`).
4. **Пороги — стартовые значения раздела 4**, срок хранения строк — уточнить по первым неделям данных.
