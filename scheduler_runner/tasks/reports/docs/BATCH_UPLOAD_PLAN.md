# План: пакетная загрузка KPI в Google Sheets и очередь несохраненных результатов

Статус: **этапы 1–2 выполнены (30.09.2026), этапы 3–4 — план**. Составлен 30.09.2026. Шаг 1 (устойчивость к 429) выполнен —
см. [ARCHITECTURE.md](ARCHITECTURE.md), раздел «Квота Google Sheets API при массовой выгрузке».

## 1. Проблема

Квота Google Sheets API — 60 чтений и 60 записей в минуту **на сервисный аккаунт**, а все ПВЗ пишут одним аккаунтом:
квота общая. Задача ReportsProcessor стартует на всех ПВЗ в 21:30, и загрузки совпадают по времени.

Загрузка сейчас построчная: `run_upload_batch_microservice` → `upload_batch_data` → `BaseUploader.batch_upload`
(цикл по строкам) → `GoogleSheetsReporter.update_or_append_data_with_config` для каждой строки.

### Сколько запросов стоит запуск сейчас (по коду)

| Операция | Чтения | Записи |
|---|---|---|
| Подключение (`open_by_key`, `worksheet()`, заголовок в `_sync_table_structure` и повторно в `_validate_table_structure` — до кэша этапа 1) | 4 | — |
| Проверка покрытия (`check_missing_items`): подключение + `col_values` (последняя строка) + `batch_get` | 6 | — |
| «Проверка подключения» перед загрузкой (`test_upload_connection`) — отдельное подключение | 3 | — |
| Подключение для загрузки | 3 | — |
| На каждую строку: поиск по ключу — заголовок, `col_values` (последняя строка), `batch_get` | 3 | — |
| На каждую новую строку: заголовок, `append_rows` без формул, 5 формул по одной (`id`, 3×`GET_REWARD`, `SUM`) | 1 | 6 |
| На каждую обновляемую строку: заголовок, `acell` (сохранение `timestamp`), `update` | 2 | 1 |
| Синхронизация `KPI_FAILOVER_STATE` (подключение, `batch_get`, запись) | ~5 | 1–2 |

**7 новых строк одного ПВЗ: ~46 чтений и ~44 записи** за несколько минут. Три-четыре ПВЗ, досылающие по 7 дат,
превышают поминутную квоту в 2–3 раза.

После шага 1 превышение квоты не теряет данные (повтор через 65+ с), но растягивает запуск и оставляет риск:
если все 5 попыток исчерпаны, результат парсинга (13–15 минут работы браузера) пропадает до следующего вечера.

## 2. Цель

1. Загрузка KPI одного ПВЗ — **константное число запросов**: 4 чтения и 2 записи при любом числе строк.
2. Результат парсинга **не теряется** при сбое загрузки: сохраняется локально и досылается следующим запуском без
   повторного парсинга.
3. Текущая построчная загрузка остается переключаемым режимом (откат без изменения кода).

## 3. Пакетный upsert KPI

### 3.1 Алгоритм (новый метод `GoogleSheetsReporter.upsert_rows_batch`)

| # | Шаг | Запросы |
|---|---|---|
| 1 | Подключение: `open_by_key`, `worksheet()`, заголовок (уже читается в `_sync_table_structure` — **кэшировать** в `self._headers`, повторно не читать) | 3 чтения |
| 2 | Один `batch_get` открытых диапазонов ключевых колонок и `timestamp`: `B2:B`, `C2:C`, `K2:K` (без отдельного `col_values` для поиска последней строки — открытый диапазон возвращает данные до последней непустой ячейки) | 1 чтение |
| 3 | В памяти: нормализация ключей (`_normalize_for_comparison`/`_prepare_value_for_search`, как сейчас), карта «ключ → номер строки», разбиение входных записей на обновляемые и новые; дубли во входных данных — побеждает последняя запись; дубли в таблице — берется первая строка, предупреждение `KPI_BATCH_DUPLICATE_ROWS` | — |
| 4 | Все новые строки одним `append_rows` **без формул** (как сейчас, позицию выбирает Google — два ПВЗ, пишущие одновременно, не затирают строки друг друга) | 1 запись |
| 5 | Номера добавленных строк — из ответа `updates.updatedRange` (`KPI!A349:K355` → 349..355). Если диапазон не разобран или число строк не совпало — один `batch_get` ключей для поиска (как fallback сейчас) | 0 (+1 чтение в fallback) |
| 6 | Один `values_batch_update` (`worksheet.batch_update([...], value_input_option="USER_ENTERED")`): для обновляемых строк — вся строка с формулами и сохраненным `timestamp` из шага 2; для добавленных — формулы (`A{n}`, `G{n}:J{n}`) с реальными номерами строк | 1 запись |

**Итого: 4 чтения и 2 записи** (1 запись, если строки только обновляются или только добавляются без формул).

Промежуток между шагами 4 и 6 (секунды) новые строки существуют без формул. Если шаг 6 не прошел, повтор загрузки
найдет эти строки на шаге 2 и допишет формулы через обновление — операция идемпотентна.

### 3.2 Результат и совместимость

Метод возвращает структуру, совместимую с текущим `batch_upload`, чтобы вызывающий код (`run_upload_batch_microservice`,
уведомления, `sync_owner_failover_state_from_batch_result`) не менялся:

```python
{
    "success": True,            # False, если хоть одна запись не сохранена
    "uploaded": 7, "failed": 0,
    "details": [{"index": 0, "result": {"success": True, "action": "appended", "row_number": 349, ...}}, ...],
    "diagnostics": {"mode": "batch", "appended": 7, "updated": 0, "read_requests": 4, "write_requests": 2,
                    "duplicate_sheet_rows": 0},
}
```

Ошибка API (после повторов транспортного клиента) — `success: False` для всех записей пакета, без частичной
неопределенности: строки либо добавлены (видно на следующей попытке через шаг 2), либо нет.

### 3.3 Устранение лишних подключений

- Coverage-check (`check_missing_items`): открытые диапазоны в `batch_get` вместо `col_values` для поиска последней
  строки (−1 чтение), как в пакетном upsert.

- `run_upload_batch_microservice`: убрать отдельную «проверку подключения» (`test_upload_connection`) — подключение
  загрузчика само является проверкой (−3 чтения).
- Кэш заголовка в `GoogleSheetsReporter` использовать и в построчных методах (`_find_rows_by_unique_keys_batch`,
  `_append_new_row`, `_update_existing_row`, `_prepare_row_values`) — полезно и для режима `row`.

### 3.4 Счетчик запросов

`QuotaBackoffHTTPClient` получает счетчики `read_requests` / `write_requests` (по HTTP-методу: GET — чтение,
POST/PUT — запись, в том числе повторы отдельно: `retries_429`, `retries_other`). После загрузки в лог Uploader:
`KPI_UPLOAD_STATS mode=batch rows=7 appended=7 updated=0 reads=4 writes=2 retries_429=0`.
Это доказывает экономию на проде и сразу показывает, упирались ли ПВЗ в квоту.

## 4. Очередь несохраненных результатов (`pending_uploads.json`)

### 4.1 Назначение

Если загрузка не удалась (исчерпаны повторы, нет сети, таймаут задачи), распарсенные строки сохраняются локально
и отправляются в начале следующего запуска — без повторного парсинга, который занимает 13–15 минут на 7 дат.

### 4.2 Файл

- Путь: `REPORTS_ROOT/pending_uploads.json` (`C:\tools\scheduler\reports\`, каталог в `.gitignore`); параметр
  `pending_uploads_path` в `BACKFILL_CONFIG` для переопределения.
- Одна задача ReportsProcessor на машину (lock-файл планировщика), поэтому межпроцессная блокировка не нужна.
- Запись атомарная: временный файл + `os.replace`.
- Формат:
  ```json
  {
    "version": 1,
    "records": {
      "ЧЕБОКСАРЫ_144|2026-09-30": {
        "record": {"work_date": "30.09.2026", "object_name": "ЧЕБОКСАРЫ_144", "issued_packages": 425,
                   "direct_flow": 58, "return_flow": 42, "timestamp": "2026-09-30 21:44:10"},
        "created_at": "2026-09-30 21:44:10",
        "attempts": 1,
        "last_error": "[429] Quota exceeded ...",
        "source_run_id": "20260930213005|ЧЕБОКСАРЫ_144"
      }
    }
  }
  ```
- В файле только данные KPI (числа выдачи и потоков) — без токенов и персональных данных.

### 4.3 Поток в `reports_processor`

1. **Начало запуска — досылка очереди** (`flush_pending_uploads`): если файл не пуст — пакетная загрузка всех записей
   (один пакет на все ПВЗ из очереди), успешные удаляются из файла, неуспешные остаются с `attempts += 1`.
2. **Проверка покрытия** — как сейчас. Даты, которые остались в очереди (загрузка не удалась снова), исключаются из
   списка для парсинга: данные уже есть локально.
3. **Парсинг** недостающих дат.
4. **Перед загрузкой** — записи сохраняются в очередь (`enqueue_pending_uploads`).
5. **Загрузка** (пакетная) → успешные записи удаляются из очереди.
6. В уведомление и в `reports_run_summary` добавляется число записей, оставшихся в очереди (`pending_uploads_left`).

Порядок «сначала в файл, потом загрузка» гарантирует сохранность данных даже при обрыве процесса по таймауту во время
загрузки. Повторная загрузка той же записи безопасна — upsert по ключу `work_date + object_name` обновляет строку.

### 4.4 Правила очереди

- Ключ записи — `object_name|work_date`; новая запись с тем же ключом заменяет старую (свежие данные важнее).
- Записи старше `pending_max_age_days` (по умолчанию 14) удаляются при досылке с предупреждением
  `PENDING_UPLOAD_EXPIRED` — это за пределами окна дозаполнения, их заново соберет только ручной backfill.
- Очередь — **только для данных своего ПВЗ**. Failover-загрузки (данные соседа) в очередь не попадают: при неудаче
  статус в `KPI_FAILOVER_STATE` — «recovery failed», как сейчас, и дату повторит логика failover
  (`max_attempts_per_date`). Так статус в таблице не расходится с содержимым очереди (см. раздел 10).

## 7. Тесты

### Unit (без сети)
- `upsert_rows_batch`: только новые строки (1 `append_rows` + 1 `batch_update`, формулы с номерами из `updatedRange`);
  только обновления (сохранение `timestamp`, 1 `batch_update`); смешанный пакет; дубли во входе; дубли в таблице;
  неразобранный `updatedRange` → fallback-поиск; ошибка `append_rows` → все записи `success: False`;
  повтор после сбоя шага 6 дописывает формулы (идемпотентность).
- Проверка числа вызовов mock-листа: ровно 1 `batch_get`, 1 `append_rows`, 1 `batch_update`, 0 `row_values`/`col_values`/`acell`.
- `pending_uploads`: атомарная запись; замена по ключу; удаление успешных; `attempts`; истечение по возрасту;
  поврежденный файл → переименование в `.corrupt` и пустая очередь с предупреждением.
- `reports_processor`: досылка в начале; исключение дат очереди из парсинга; enqueue до загрузки; очередь сохраняется
  при неуспешной загрузке. Существующие тесты режима `row` проходят без изменений.

### На тестовой таблице (`SPREADSHEET_ID_TEST`, лист `KPI`, сейчас пустой)

  `GOOGLE_SHEETS_RETRY` с остальными; проверка дубликатов `debug/kpi_last_dates.py` и в таблице.

## 10. Принятые решения (30.09.2026)

1. **Failover и очередь — failover-данные в очередь не попадают.** Альтернативы (новый статус
   `failover_pending_upload` или обновление статуса при досылке) требуют изменений в политике и арбитраже failover.
   Текущая логика уже повторяет неудавшуюся дату (`max_attempts_per_date`), а failover срабатывает редко — повторный
   парсинг чужой даты дешевле, чем рассогласование статуса и очереди. Пересмотреть, если failover станет частым.
2. **Отдельный сервисный аккаунт на ПВЗ — не делаем.** Оптимизация решается сокращением числа запросов. Остается
   возможностью на будущее: код не меняется (путь к ключу в конфиге), нужны ключи и доступ к таблице.
3. **Увеличение квоты в Google Cloud Console — не делаем** по той же причине.

## 11. Результаты этапа 2 и открытые вопросы (30.09.2026)

- Smoke `tests/run_kpi_batch_upload_smoke.py` на тестовой таблице: 3 полных прогона и 5 циклов «7 новых строк →
  немедленный повтор» — без ошибок: `reads=4 writes=2`, затем `reads=4 writes=1`, `timestamp` сохранен, дубликатов нет,
  параллельная запись двух процессов корректна.
- **Не объяснен один случай** в самом первом прогоне на тестовой таблице: при повторе 6 из 7 строк найдены и
  обновлены, одна добавлена повторно (дубликат). Не воспроизвелся в 8 последующих прогонах. Проверено и исключено:
  выравнивание открытых диапазонов (ведущие пустые ячейки сохраняются), нормализация ключей, гонка «добавление → сразу
  чтение». Меры: предупреждение `KPI_BATCH_DUPLICATE_ROWS` при чтении ключей, поиск дубликатов в
  `utils/parser/docs/debug/kpi_last_dates.py`, включение `batch` сначала на одном ПВЗ.
- Выявлено в режиме `row`: `BaseUploader.batch_upload` возвращает `success: True`, даже если часть строк не записалась,
  и не заполняет `error` — повтор загрузки при 429 на уровне строк не срабатывает. Режим `batch` возвращает честные
  `success` и `error`. Режим `row` оставлен без изменений как путь отката.
- Не сделано на этапе 2 (перенесено): открытые диапазоны в coverage-check вместо `col_values` (п. 3.3).
- **Проверка на боевой таблице (30.09.2026):** ручной прогон ядра процессора для ЧЕБОКСАРЫ_144 за 16–22.09 (7 дат,
  без уведомлений и `KPI_FAILOVER_STATE`), загрузка в режиме `batch`: 7 строк добавлены (строки 349–355), за весь запуск
  9 чтений (coverage-check 5 + загрузка 4) и 2 записи, формулы `id`/`GET_REWARD`/`SUM` ссылаются на свои строки,
  награды рассчитаны, дубликатов в листе нет. После этого `batch` включен для 144 (`kpi_upload_mode_by_pvz`).
