## 1. Зачем

Каждый ПВЗ вечером (21:30) собирает свои KPI за последние 7 дней и загружает недостающие даты в лист `KPI`. Failover —
страховка: если ПВЗ не смог собрать свои данные, это делает ПВЗ-помощник, у учетной записи которого есть доступ к чужому
ПВЗ (карта `FAILOVER_POLICY_CONFIG.priority_map`, например 143, 182, СОСНОВКА_10 → помощник 144).

Сценарии отказа владельца:

| # | Что случилось у владельца | Что видно в таблице | Помощь сейчас |
|---|---|---|---|
| S1 | Запуск был, часть дат не собрана (сбой страницы, `PARTIAL_DATE_REJECTED`) | `owner_failed` по этим датам | работает |
| S2 | Запуск был, **ни одна дата не собрана** (отозвана сессия, сломан выбор ПВЗ — как 30.09.2026) | ничего | **не работает** |
| S3 | Запуска не было (компьютер выключен, оператор не вошел в Windows, сбой до записи состояния) | ничего | **не работает** |
| S4 | Данные собраны, загрузка в Google Sheets не прошла | `owner_failed` (если запись состояния прошла) | частично |

Сейчас failover закрывает только S1, а самые частые реальные отказы — S2 и S3.

## 4. Целевая схема

```text
Владелец (каждый ПВЗ, 21:30)
  1. coverage-check своих 7 дней → missing dates
  2. парсинг + загрузка
  3. ВСЕГДА пишет итог по своим missing dates: owner_failed (с причиной) / owner_success (только после инцидента)
     — в том числе когда не собрано ничего (P1)
  4. failover-проход как помощник — только если своя сессия жива (хотя бы одна своя дата собрана или своих дат нет)

Помощник (failover-проход)
  a. кандидаты из KPI_FAILOVER_STATE: owner_failed / failover_failed / failover_claimed с истекшим сроком (P4),
     только даты в окне 7 дней (P5)
  b. «молчащие» соседи (P2): один batched coverage-check KPI по ПВЗ, где помощник есть в priority_map,
     даты окна СТРОГО ДО сегодняшней — сегодняшнюю дату сосед, возможно, еще собирает
  c. захват через Apps Script; для «молчащей» даты строка создается атомарно в том же вызове (P3)
  d. парсинг соседа → повторный coverage-check → загрузка → failover_success / failover_failed
  e. в конце — переключение учетной записи обратно на свой ПВЗ (P6)
```

**Почему сегодняшняя дата молчащего соседа не берется.** Все ПВЗ стартуют в 21:30, проход помощника начинается после его
собственной работы (~21:45), сосед в это время может еще загружать свою дату. Если сосед действительно не работал,
его сегодняшняя дата станет «вчерашней» на следующий вечер и будет восстановлена — для страховочной копии задержка в
сутки допустима. Явный `owner_failed` за сегодня (сосед запускался и сообщил об ошибке) обрабатывается сразу.

**Гонка владелец ↔ помощник.** Владелец, вернувшийся после простоя, догружает свои прошлые даты в тот же вечер, когда
помощник может их восстанавливать. Защита: помощник перед загрузкой повторяет coverage-check (уже есть), пакетная загрузка
читает ключи непосредственно перед добавлением — окно гонки сокращается до секунд. Остаточный риск — редкий дубликат
строки; его показывают `KPI_BATCH_DUPLICATE_ROWS` и `utils/parser/docs/debug/kpi_last_dates.py`. Полная блокировка
(владелец захватывает свои даты) добавила бы по записи на каждый ПВЗ каждый день — не делаем, пока дубликаты не появятся.

### Этап A. Владелец всегда сообщает о сбое (P1) ✅

Сделано 01.10.2026 (`reports_processor.py`, `owner_state_sync.py`, `reports_upload.py`, `reports_summary.py`).
Дополнительно найдено и закрыто: при `parser_api=legacy` (по умолчанию) падение парсера (браузер, `AUTH_REQUIRED`)
выбрасывало исключение из процессора — запуск завершался без записи состояния и без уведомления. Теперь

с ошибкой пакета или `parse_result_missing`.

- `reports_processor.py`: синхронизация состояния владельца выполняется при любом исходе, если были missing dates.
  Ошибки парсинга → `owner_failed` с причиной из `batch_result`; ошибка загрузки → `owner_failed` с ошибкой загрузки
  (логика уже есть в `build_owner_final_failover_state_records`, мешает только условие в процессоре).
- «Нет данных для загрузки» перестает быть ошибкой загрузки: загрузка пропускается, итог определяется ошибками парсинга.
- Failover-проход пропускается, если **все** свои даты не собраны (сессия Ozon мертва — помочь соседу тем же браузером
  нельзя) или не прошла загрузка (Google Sheets недоступен). Причина пишется в лог: `FAILOVER_PASS_SKIPPED reason=...`.
- Тесты: единичные на ветки процессора (все даты не собраны / часть / загрузка упала).
